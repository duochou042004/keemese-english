# ADR-0008: Bilingual UI with i18next / react-i18next

Status: Accepted (2026-10-17)

## Context
The product owner requires Vietnamese and English (PD-09). Tutor-entered content is not translated (assumption A6). Only two languages, and Vietnamese has no plural forms.

## Decision
- **`i18next` + `react-i18next`** (checked 2026-10-17: 26.x and 17.x), JSON catalogs at `web/src/locales/{vi,en}/{common,tutor,student,errors}.json`, typed keys via TypeScript module augmentation. No ICU plugin until a message needs it.
- Language resolution: the user's saved preference (server) → the pre-login choice in `localStorage` (`lang`, which is not a credential) → `navigator.language` (`vi*` → `vi`, otherwise `en`). Default `vi`.
- Formatting uses `Intl` with locales `vi-VN` and `en-GB` (day-month-year order in both languages, so switching never flips the meaning of `03/04`).
- **The API never returns user-facing prose.** Errors carry stable `code`s (for example `students.username_taken`) that map to keys in `errors.json`. Validation errors carry field-level codes.
- A Vitest unit test asserts both catalogs have identical key sets (NFR-I18N-01).

## Alternatives
- Lingui: compile-time extraction and smaller runtime, but a macro and extraction workflow agents get wrong more often. The gain is marginal for two languages.
- FormatJS / react-intl: ICU-first and verbose for this need.
- Paraglide: tree-shakable, but less ecosystem guidance.

## Consequences
- Vietnamese strings run longer than English ones, so layouts are QA'd in both languages ([visual QA](../testing/strategy.md#visual-qa)).
- Every UI PR that adds text must add both `vi` and `en` keys (the parity test enforces it).

## Revisit when
A third language is requested, or the catalogs grow past about 1,500 keys.
